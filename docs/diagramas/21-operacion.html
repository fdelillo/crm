Preparación y arranque

El operador prepara la base antes de arrancar el runtime; serve no ejecuta migraciones automáticamente.

Es una secuencia operativa documentada. Bootstrap ocurre por clúster; migrate usa credenciales de dueño; serve usa el pool crm_app.

Apagado ordenado

La cancelación detiene HTTP y métricas, permite drenar requests y espera al worker antes de cerrar el pool.

ShutdownTimeout = SendBudget + 5 s = 25 s para cada espera indicada; no es una promesa de 25 s para todo el proceso de apagado.

Restauración en otro clúster

El runbook contempla datos, roles de empresa y verificación antes de devolver tráfico.

Runbook documentado, no automatización de backup desplegada. El plan fija el tratamiento de roles; frecuencia, retención y RPO/RTO no están definidos.

Cómo leer esta vista

  • GET /healthz no toca la base. GET /readyz limita adquisición y lectura a 1 s y exige coincidencia exacta del esquema; responde 503 ante fallo o versión distinta.
  • pg_dump no incluye roles: el plan pide datos más roles, o respaldo físico/PITR del clúster. Para otro clúster: bootstrap, restore y crm tenants reprovision-roles.
  • La reprovisión es idempotente, bloquea ejecuciones simultáneas y usa una transacción por empresa; continúa con otras empresas si una falla y reporta el resultado.
  • Los objetos privados también necesitan respaldo coherente con sus referencias. No se afirma que el repositorio tenga un job de backup ni objetivos de recuperación aprobados.
  • Si falla vulncheck, Error 1 requiere reejecutar el job y no volverlo opcional; Error 3 requiere tratar el hallazgo. Para vulnerabilidades ajenas al PR: rama y PR propios desde main, integrados antes que otros; estándar Go: subir toolchain en ambos mod; módulo: actualizar a la versión corregida. Sin corrección: dejar de usar el símbolo, reemplazar dependencia o pedir al usuario la aceptación del riesgo. La aceptación se registra en docs/seguridad/vulnerabilidades-aceptadas.md, con vencimiento máximo de 30 días y una exclusión por id con vencimiento diseñada en ese primer caso. El archivo aún no existe; es una ruta prevista, no un enlace. El binario desplegado sigue vulnerable hasta el despliegue corregido.
  • Un cambio de esquema afecta readiness de instancias con binarios incompatibles. P-1 debe cerrar el procedimiento concreto de despliegue, rollback y hosting.
