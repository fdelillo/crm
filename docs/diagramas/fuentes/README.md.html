  57 ## Desarrollo
  58 
  59 Requisitos: Go 1.27 (con `GOTOOLCHAIN=auto` el comando `go` descarga la versión fijada en `go.mod`),
  60 Docker, `make`, y [`mkcert`](https://github.com/FiloSottile/mkcert#installation) para HTTPS local.
  61 `sqlc` y `golangci-lint` no se instalan: `make` los corre desde `tools.mod` (`go tool -modfile=tools.mod`).
  62 
  63 ### Comandos
  64 
  65 | Comando | Qué hace |
  66 |---------|----------|
  67 | `make check` | `lint` + `test` + `test-int`. Es el checkpoint de cada fase; no necesita mkcert |
  68 | `make lint` | `gofmt`, `go vet`, `golangci-lint` (con `depguard`) y `sqlc diff` |
  69 | `make test` | Tests unitarios (`go test -race ./...`); no necesitan Docker |
  70 | `make test-int` | Además, tests de integración con PostgreSQL 18 real (necesita Docker) |
  71 | `make generate` | Regenera el código de `sqlc` |
  72 | `make db-reset` | Solo desarrollo: recrea el PostgreSQL local, corre el bootstrap y las migraciones |
  73 | `make dev-certs` | Solo desarrollo y E2E: genera `.certs/localhost.pem` y `.certs/localhost-key.pem` con mkcert |
  74 
  75 ### Primera vez
  76 
  77 1. Instalar `mkcert`. En Linux instalar también `certutil` (paquete `libnss3-tools` o equivalente).
  78 2. `mkcert -install` (una vez por equipo: crea una CA local y la agrega a los navegadores).
  79 3. `make dev-certs` (genera el certificado de `localhost` y `127.0.0.1`; `.certs/` no se versiona).
  80 4. `cp .env.example .env` y reemplazar `AUTH_HMAC_KEY` (`openssl rand -base64 32`).
  81 
  82 > **No compartas ni copies al repositorio `rootCA-key.pem`** (está en `mkcert -CAROOT`): con esa
  83 > clave se puede interceptar el HTTPS de tu equipo. La CA es de cada persona.
  84 
  85 ### Levantar todo
  86 
  87 ```sh
  88 docker compose up -d --wait        # PostgreSQL 18 (con los roles y la base), Mailpit y MinIO
  89 set -a && . ./.env && set +a       # carga la configuración en el shell
  90 go run ./cmd/crm migrate up        # migraciones, con el rol crm_owner
  91 go run ./cmd/crm serve             # loguea listen=https_local
  92 curl https://localhost:8443/healthz   # sin -k: {"status":"ok"}
  93 ```
  94 
  95 `--wait` deja también creado el bucket de desarrollo (`S3_BUCKET`, por defecto `crm-dev`): el
  96 healthcheck de MinIO lo crea de forma idempotente, incluso después de `docker compose down -v`.
  97 
  98 Hasta que exista el frontend embebido, `https://localhost:8443/` responde `503` ("La interfaz no
  99 está compilada"): es esperado.

 101 ### Probar el registro (Fase 3)
 102 
 103 Con los servicios y el backend levantados como arriba:
 104 
 105 ```sh
 106 curl -c /tmp/crm-cookies.txt -H 'Content-Type: application/json' \
 107   --data '{"name":"Ana","email":"ana@example.com","password":"una-clave-segura-123","company_name":"Mi Empresa","base_currency":"ARS","industry_template_code":"generic"}' \
 108   https://localhost:8443/api/v1/auth/signup
 109 curl -b /tmp/crm-cookies.txt https://localhost:8443/api/v1/me
 110 ```
 111 
 112 El registro responde `201`, `/me` devuelve el usuario `admin` con sus 15 permisos y el correo de
 113 verificación aparece en [Mailpit](http://localhost:8025). El adaptador SMTP usa por defecto
 114 `localhost:1025` y `no-reply@crm.local` en modo local; `SMTP_HOST`, `SMTP_PORT` y `SMTP_FROM`
 115 permiten cambiarlos.

 117 ### Modos de desarrollo (plan 001, §10.5.1)
 118 
 119 La sesión es una cookie `__Host-` `Secure`, así que el navegador solo la guarda por HTTPS. En
 120 desarrollo `APP_BASE_URL` es siempre `https://`; `TLS_CERT_FILE` y `TLS_KEY_FILE` solo se aceptan
 121 cuando el host es `localhost` o `127.0.0.1`.
 122 
 123 | Modo | `crm serve` | El navegador abre | `APP_BASE_URL` |
 124 |------|-------------|-------------------|----------------|
 125 | Binario completo (y E2E) | `HTTP_ADDR=:8443` con `TLS_CERT_FILE` y `TLS_KEY_FILE` | `https://localhost:8443` | `https://localhost:8443` |
 126 | Vite + API | igual que arriba | `https://localhost:5173` (Vite con el mismo certificado; *proxy* de `/api` a `https://localhost:8443`) | `https://localhost:5173` |
 127 | Solo backend (`curl`, sin navegador) | sin `TLS_*` (HTTP plano en `:8080`) | — | `https://localhost:8080` |
 128 
 129 Node no usa el almacén de certificados del sistema: para que el *proxy* de Vite y los scripts de
 130 Node confíen en el certificado, exportar
 131 `NODE_EXTRA_CA_CERTS="$(mkcert -CAROOT)/rootCA.pem"`.

 133 ### Base de datos: bootstrap y migraciones (ADR-004)
 134 
 135 Son dos mecanismos:
 136 
 137 - **Bootstrap** (`db/bootstrap/`): crea los roles del clúster y la base `crm`. Lo corre un DBA una
 138   vez por clúster; en desarrollo, lo ejecuta el contenedor de PostgreSQL al inicializarse. Es
 139   idempotente y necesita `psql`. Las contraseñas de `crm_owner` y `crm_app` **no** están en el
 140   script: se toman de `CRM_OWNER_PASSWORD` y `CRM_APP_PASSWORD` si están definidas.
 141 
 142   ```sh
 143   psql -v ON_ERROR_STOP=1 -U postgres -d postgres -f db/bootstrap/001_roles_and_database.sql
 144   ```
 145 
 146 - **Migraciones** (`db/migrations/`, goose embebido en el binario): `crm migrate up|down|status`,
 147   siempre con `DATABASE_MIGRATION_URL` (rol `crm_owner`), como paso de despliegue.
 148 
 149 Los roles son globales al clúster: **un clúster de PostgreSQL por entorno**, y los respaldos
 150 necesitan también los roles (`pg_dumpall --roles-only`) o un backup físico del clúster.
