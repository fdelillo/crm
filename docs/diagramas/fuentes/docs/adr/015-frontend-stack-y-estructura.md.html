   1 # ADR-015: Stack base y estructura del frontend (Vite + React + TypeScript, `web/`, carpetas por feature)
   2 
   3 **Status**: Proposed
   4 **Fecha**: 2026-09-29
   5 **Origen**: spec 001 (`specs/001-empresas-usuarios/ui.md` §0, §9, §22)
   6 
   7 ## Contexto
   8 
   9 La constitución fija React + TypeScript como PWA mobile-first. El backend es un monolito Go que
  10 sirve la API en `/api/v1` con sesión por cookie en el mismo origen (ADR-006) y va a servir también
  11 la SPA (ADR-019). No hay requisitos de SEO (todo está detrás de un login) ni de renderizado en el
  12 servidor. El usuario tiene nivel básico en React/TypeScript: cada herramienta y cada capa propia es
  13 algo más que aprender. Hay 10 specs en el MVP: la estructura tiene que aguantar decenas de
  14 pantallas sin volverse una pila de carpetas `components/`, `hooks/` y `utils/` globales.
  15 
  16 ## Decisión
  17 
  18 1. **Build con Vite** (última estable, ≥ 8), plantilla React + TypeScript, **SPA sin SSR**. `npm`
  19    como gestor de paquetes; Node LTS fijado en `engines` y `.nvmrc`.
  20 2. **TypeScript estricto**: `strict`, `noUncheckedIndexedAccess`, alias `@/*` → `src/*` (lo exige
  21    shadcn). React 19.
  22 3. **Ubicación**: carpeta `web/` en la raíz del mismo repositorio. `web/dist/` es el resultado del
  23    build; el paquete Go `web` (`web/embed.go`) lo embebe (ADR-019).
  24 4. **Organización por feature con *colocation*** dentro de `web/src/`:
  25    - `app/`: router, `QueryClient`, layout raíz, shell, guards, error boundary.
  26    - `api/`: cliente HTTP, errores, mensajes por `code`, claves de caché y tipos **generados**.
  27    - `features/<dominio>/`: pantallas, componentes, hooks, esquemas y tests de cada dominio, con
  28      los nombres del glosario (`auth`, `tenant`, `users`, luego `parties`, `projects`…).
  29    - `components/`: presentación compartida; `components/ui/`: componentes generados por shadcn.
  30    - `lib/`: funciones puras transversales (formato, CUIT, rutas seguras).
  31    - Tests junto al archivo que prueban (`LoginPage.test.tsx`).
  32 5. **Fronteras verificadas por lint** (`no-restricted-imports` de ESLint): `components/` no
  33    importa `api/`, `features/` ni `app/`; una feature no importa otra salvo `features/auth/session`;
  34    solo `api/` hace requests.
  35 6. Herramientas de calidad: ESLint (typescript-eslint, `react-hooks`, `jsx-a11y`, `no-console`),
  36    Prettier, `tsc -b` como *typecheck*. Script único de checkpoint: `npm run check`.
  37 
  38 ## Fundamento
  39 
  40 - Sin SEO ni SSR, una SPA es lo más simple de construir, probar y desplegar: el binario Go solo
  41   tiene que servir archivos estáticos.
  42 - Vite es el estándar actual para SPAs React: servidor de desarrollo rápido, build de producción
  43   optimizado, *proxy* de desarrollo incorporado (lo necesita ADR-019) y Vitest comparte su
  44   configuración (ADR-022).
  45 - TypeScript estricto convierte los tipos generados del contrato en documentación ejecutable: el
  46   error más común del frontend (suponer que un campo llegó) lo marca el editor. Para quien está
  47   aprendiendo, el editor enseña.
  48 - Mismo repositorio: un cambio de contrato, backend y frontend va en un solo PR y la CI los
  49   verifica juntos; el contrato vive en `specs/`, a un `../` de distancia.
  50 - Por feature: lo que cambia junto vive junto; agregar una spec es agregar una carpeta. Es el
  51   mismo criterio que ADR-001 aplica al backend (paquetes por dominio).
  52 
  53 ## Alternativas consideradas
  54 
  55 - **Next.js / React Router en modo framework / Remix**: SSR, rutas por archivos y servidor Node.
  56   Sin requisito que lo justifique; agregan un runtime de servidor que el binario Go no puede
  57   embeber como archivos estáticos, y muchos conceptos más (componentes de servidor, loaders).
  58 - **Rsbuild / Parcel / webpack**: funcionan, pero con menos documentación y ejemplos para
  59   shadcn/Tailwind v4 y sin la integración directa con Vitest.
  60 - **pnpm o yarn**: más rápidos o estrictos, pero `npm` viene con Node y es lo que asume casi toda
  61   la documentación; la diferencia no importa a esta escala.
  62 - **Repositorio separado para el frontend**: contrato y cambios coordinados en dos repos, dos CI,
  63   versiones cruzadas; sin beneficio para un equipo chico con un único binario.
  64 - **Frontend dentro de `internal/`**: mezcla un proyecto Node con paquetes Go internos; `web/` es
  65   la convención más reconocible.
  66 - **Carpetas por tipo técnico** (`components/`, `hooks/`, `services/` globales): cada feature se
  67   dispersa en cinco carpetas y crecen sin límite; escala mal pasada una decena de pantallas.
  68 - **JavaScript sin tipos**: menos que aprender al principio, pero se pierde la derivación de tipos
  69   del contrato, que es la garantía principal entre frontend y backend.
  70 
  71 ## Consecuencias
  72 
  73 - Ganás: un proyecto convencional (lo que muestran los tutoriales de Vite + React + shadcn),
  74   fronteras verificadas por lint, tipos del contrato de punta a punta.
  75 - Aceptás: Node en la máquina de desarrollo y en CI además de Go; el binario de producción
  76   necesita que el frontend se compile antes (`make build`, ADR-019); TypeScript estricto exige
  77   manejar `undefined` explícitamente (más código, menos errores).
